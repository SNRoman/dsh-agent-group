# Agent Workspace v0.3.0 Compatibility and Extension Foundation Design

## Status

Approved in chat on 2026-09-02 as the third stage of the three-stage roadmap; the product owner delegated implementation design and code organization. It depends on the `0.2.0` product surface and its stable projections.

## Goal

Move Agent Workspace from one implicit local aggregate to an explicitly managed set of portable workspaces with recoverable backups, tested DSH compatibility, and a narrow external extension API. The release preserves the existing behavioral model and keeps the plugin additive and uninstallable.

## Non-goals

This release does not add hard room secrecy, permanent child-agent identities, unmentioned automatic speech, per-agent model/tool/skill restrictions, cloud synchronization, real-time multi-user editing, arbitrary third-party mutation hooks, or compatibility shims for unsupported DSH versions.

## Multi-workspace Model

### Workspace directory

Each workspace aggregate gains descriptor metadata containing:

- branded workspace id;
- user-visible label;
- lifecycle state `active` or `archived`;
- optional creation provenance for newly created/imported records, left unknown for migrated legacy data;
- application-level aggregate record version.

The Host derives the workspace directory by listing the `workspaces` table; it does not maintain a second catalog record. The current DSH storage-domain table guarantees atomicity for one record but not across a catalog record and aggregate record, so keeping the descriptor and aggregate together makes create, rename, archive, import, and migration each one atomic record operation.

The Browser selects one active workspace at a time. Every snapshot, mutation, stream subscription, runtime item, page cursor, and export request carries that workspace id. The Host must never infer `local` as the active selection after migration.

Labels are not identifiers and may repeat across workspaces. Renaming a workspace does not change its id, session bindings, memory, or room history.

Last activity is derived from aggregate revision and the greatest event sequence instead of stored twice. Migration never uses its execution time as a fabricated legacy creation time.

### Runtime isolation

Employee pools, dispatcher queues, turn trackers, turn streams, and direct-room reuse live in one runtime capsule per workspace. Runtime maps use workspace id plus entity id wherever they cross a capsule. This is required because aggregates mint local ids and two workspaces may contain the same `agent-1`, `room-1`, or event id. The same human-readable agent or room name may exist in different workspaces. A session binding belongs to exactly one workspace agent and cannot be admitted into another workspace through a guessed id.

Archiving first commits the descriptor state `archived`; every new admission validates that state from its serialized current record. A workspace-specific quiescence operation then handles work already admitted. In `stop` mode it removes every exact queued workspace message from employee inboxes, cancels exact active turns after their unrelated queues are preserved, and aborts active children. In `wait` mode it permits the already-admitted queue/turn/child set to drain while admitting nothing new. The operation completes only after the capsule proves that no queued or active work remains. It does not delete durable data or reuse single-turn stop as a substitute for workspace quiescence.

### Application-level record migration

The DSH storage domain remains version `0` because the current storage-domain API rejects a changed domain version and provides no migration hook. The aggregate gains a monotonic application-level `recordVersion`; its reader accepts the released unversioned record and the new versioned record. First start performs one deterministic per-record migration:

1. if a legacy `local` record exists without descriptor metadata, retain `local` as its stable workspace id and add the default descriptor metadata inside that record;
2. preserve the aggregate's internal ids, revision, event sequences, memories, task records, employment periods, and session bindings;
3. validate the transformed record and all cross-record relationships;
4. replace that one record atomically or leave it untouched;
5. use `recordVersion` as the idempotent migration marker.

The migration never merges two workspaces or silently discards an invalid legacy record. An invalid source produces a diagnostic and requires backup/recovery action.

## Backup, Export, and Import

### Export format

An export is a UTF-8 JSON document with a stable top-level envelope:

- format name and monotonic format version;
- plugin version and compatible import range;
- exported workspace descriptor;
- complete portable workspace aggregate with installation-local session bindings removed;
- SHA-256 integrity digest over RFC 8785 JSON Canonicalization Scheme UTF-8 bytes of the envelope excluding the digest field;
- export timestamp as metadata only.

The exporter does not read credential/configuration stores, environment variables, filesystem paths, transient turn streams, live abort handles, Browser state, or DSH session contents outside the plugin-owned aggregate. Session binding ids are cleared because they are installation-local; imported agents materialize fresh DSH sessions while retaining workspace memory. Definition instructions, messages, tool-derived event text, and child results are user content and may themselves contain sensitive material, so the confirmation UI states that the export contains the complete workspace history and must be handled accordingly.

An advanced diagnostic export may report binding presence without exporting the opaque ids.

### Import modes

Import validates byte limits before JSON parsing, then strictly validates the envelope, format version, digest, aggregate schema, complete relationship/counter invariants, identifier uniqueness, and remaining resource limits before writing. The document's source plugin version and claimed compatibility range are diagnostic metadata, not authority for acceptance.

The supported mode creates a new workspace with a new top-level workspace id while preserving internal event and entity ids inside that isolated aggregate. Import never overwrites or merges into an existing workspace in `0.3.0`. Export acquires the runtime capsule's admission barrier, blocks new deliveries/tasks/children, confirms that queued and active registries are empty, captures one aggregate revision, then releases the barrier. A crash-left `running` child must be explicitly repaired to a terminal cancelled/failed state before export or import can proceed.

The user previews the label, counts, source plugin version, excluded session bindings, and validation warnings before confirming and may choose a new label. Confirmation carries an opaque import-operation id. Workspace create/import operations run through one Host-wide directory mutation queue; inside that queue the Host returns the workspace already bearing a repeated operation id or writes exactly one new record. This provides idempotent uncertain retry despite the storage table lacking cross-record create-if-absent. Validation failure writes nothing.

### Backup operation

The Browser offers download export and import from a selected local file. The Host also exposes a scriptable service/API that returns or accepts the same validated document. Automated scheduled backup storage is out of scope; the format and API make it possible for later extensions.

## DSH Compatibility Matrix

### Declaration

The release extends the machine-readable compatibility file introduced in `0.1.1` into a result matrix listing:

- plugin version;
- supported DSH package range;
- exact DSH release commits/versions verified;
- Node and pnpm versions used;
- Host, Web, clean-profile, browser-flow, migration, and import/export results;
- known unsupported versions with a concise reason when useful.

Package peer ranges, README compatibility text, CI jobs, and release notes derive from or validate against this one matrix. They may not drift independently.

### CI policy

Required jobs run the smallest representative set:

- lowest supported DSH release;
- highest supported stable DSH release;
- each supported Node major;
- packed-artifact clean-profile and browser workflow;
- upgrade from the latest `0.1.x` and `0.2.x` stored fixture;
- export on the previous supported plugin version and import on the candidate version.

An allowed-failure canary tracks DSH's next prerelease or main branch through the explicit source mode. Canary failure reports impending incompatibility but does not widen the published peer range or block a patch release until that DSH point is declared supported.

Removing a DSH package or public API is handled by a deliberate compatibility release, not an implicit sibling-link failure.

## External Extension API

### Principles

Extensions receive stable read projections and register additive actions or presentation. They do not access the mutable aggregate, storage table, employee handles, raw Cordis context, abort controllers, credentials, or Browser stores.

All registrations are effects and return disposers. Extension ids are namespaced and duplicate registration fails at load.

### Host extension surface

The Host exports a versioned service definition with:

- read-only workspace catalog and snapshot access;
- filtered event subscription scoped by workspace id;
- registration of task or memory annotations that produce namespaced, schema-validated plugin events;
- registration of explicit human-invoked actions with validated request/result schemas;
- capability/version negotiation.

External actions cannot impersonate a human or agent. Invocation context supplies the authenticated workspace actor chosen by Agent Workspace, and the extension declares which actor classes it accepts. No extension receives a generic `execute(WorkspaceCommand)` method.

Extension persistence uses one core-owned `extension/event` workspace-event variant rather than reopening `WorkspaceEvent.type` to arbitrary strings. Its envelope contains a namespaced extension id, extension event type, payload format version, and bounded JSON payload. A registered producer's schema validates the payload before append. Durable loading validates the generic JSON envelope without requiring that extension to remain installed, so uninstalling it cannot make historical workspace data unreadable. This new event representation is introduced through the `0.3.0` application-level `recordVersion` migration.

### Browser extension surface

The Web package exports additive registries for:

- workspace navigation panels;
- task and memory detail disclosures;
- renderers for namespaced extension events;
- contextual human-invoked actions.

Renderers receive serializable read models and locale helpers. They cannot replace the Conversations, Colleagues, Tasks, or Memory owners. Unknown extension records use a generic safe fallback so uninstalling an extension does not make the workspace unreadable.

### Versioning

The extension API has its own monotonic major version independent of npm package major versions. Registration declares the API range it consumes. Unsupported ranges fail during plugin load with a diagnostic naming both versions.

Additive optional fields and new registry categories may ship within one API major. Changed actor authority, mutation semantics, or persisted extension-event representation requires a new API major and migration guidance.

## Security and Resource Limits

- Workspace ids, entity ids, export documents, page cursors, and extension payloads are validated at their parser, wire, and durable boundaries.
- Import limits bound document bytes, entity counts, event count, string sizes, and nested extension payload depth before allocation-heavy processing.
- Export filenames are derived from sanitized labels; labels never become filesystem paths on the Host.
- Integrity digests detect corruption, not authorship. The UI does not describe an unsigned export as trusted.
- Extensions receive no secrets and must use ordinary DSH capability injection for any separately authorized capability.
- A workspace-scoped action cannot reference an entity owned by another workspace.

Deployment-varying import limits are validated Host configuration fields, including maximum document bytes, aggregate records, events, string bytes, and extension-payload depth. The parser enforces them in allocation-safe order. RFC 8785 canonicalization and digest verification have fixed cross-language test vectors; these protocol choices are not deployment tunables.

## Error Handling and Recovery

- Descriptor key/id mismatches, duplicate import-operation ids, and invalid directory records fail startup with the exact workspace id and relationship; they are never silently repaired.
- Migration and import use atomic commits and are idempotent across restart.
- Archive with active work reports the affected agents/turns and requires an explicit stop-or-wait choice.
- Unsupported export or extension API versions fail before mutation and retain the source file.
- Corrupt exports report digest or schema failure without disclosing the document body in logs.
- Unknown extension events remain inspectable through a generic renderer after the extension is removed.
- A DSH canary failure creates compatibility evidence but does not alter package manifests automatically.

## Testing Strategy

### Multi-workspace and migration

- migrate an unmodified `0.1.x` single `local` fixture exactly once;
- preserve ids, sequences, memory, employment, tasks, and imported definitions;
- isolate names, direct rooms, queues, sessions, streams, and cursors across two workspaces;
- reject cross-workspace ids and mutations;
- archive/reopen behavior with idle and active work;
- atomic failure on invalid legacy records.

### Export/import

- deterministic canonical export and digest verification;
- credential/configuration/environment/path sources, transient state, and session bindings are not additionally collected, while the sensitive-content warning covers user workspace history that remains present;
- round-trip semantic equality excluding the new workspace id and bindings;
- preview/relabel and create-new-only behavior, including idempotent import-operation retries;
- corrupt, oversized, unsupported, and relationship-invalid files write nothing;
- previous supported format imports successfully.

### Compatibility matrix

- matrix/schema validation and manifest/README/CI consistency;
- lowest/highest DSH release jobs;
- Node matrix and clean registry install;
- previous-version storage upgrade and export/import forward compatibility;
- non-blocking prerelease canary evidence.

### Extension API

- effect disposal, namespace collision, capability negotiation, and unsupported API failures;
- actor authority and workspace scope cannot be forged;
- extension schema rejects invalid wire and durable data;
- Browser panels/actions are additive and core owners remain unchanged;
- unknown/uninstalled extension event fallback remains readable.

## Acceptance Criteria

`0.3.0` is complete when:

1. a legacy single workspace migrates atomically and restarts without repeating migration;
2. users can create, rename, switch, archive, and reopen isolated workspaces;
3. export/import performs a validated create-new round trip without collecting credential/configuration/environment/path sources or carrying stale DSH session bindings, while preserving user workspace content under an explicit sensitive-content warning;
4. a machine-readable compatibility matrix controls published ranges and passes required release points;
5. one reference Host extension and one Browser extension use only the public versioned API;
6. removing the reference extension leaves its historical records safely readable;
7. equal agent rights and all existing mention, delegation, child, memory, and employment rules remain unchanged;
8. migration, security, compatibility, extension, assembled browser, and release gates pass.
