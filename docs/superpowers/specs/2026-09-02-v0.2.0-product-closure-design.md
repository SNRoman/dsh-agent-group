# Agent Workspace v0.2.0 Product Closure Design

## Status

Approved in chat on 2026-09-02 as the second stage of the three-stage roadmap; the product owner delegated implementation design and code organization. It depends on the `0.1.1` stability baseline.

## Goal

Expose the already-established task, personal memory, live execution, and definition-revision concepts as one coherent browser product. A user should be able to manage a company-like workspace without relying on internal APIs or inspecting the durable aggregate.

## Product Rules Preserved

- An agent definition is a reusable role; named agents are independent instances of one selected definition revision.
- Agents have only `employed` and `departed` employment states.
- Every agent has one unified personal memory assembled from events it experienced, independent of the room or task that produced them.
- Group history admission is selected by the human when joining an agent.
- A mentioned agent must reply; an unmentioned agent never speaks automatically.
- Agents may mention peers.
- A root task is started only by a human assignment. A peer-derived task may wake its assignee only when the assigning agent holds the human's explicit delegation grant for that root.
- An agent may delegate peer work only under that explicit human grant.
- A top-level agent may create a one-shot child itself or ask the human first according to the task context; child runs do not become colleagues.
- Model, tool, and skill access remains equal for all top-level agents and is not configurable per definition or instance.

## Navigation and Information Architecture

The additive Agent Workspace overlay has four primary views:

1. **Conversations** — existing group/direct messaging and live replies;
2. **Colleagues** — definitions, revisions, named agents, and employment lifecycle;
3. **Tasks** — root tasks, assignments, delegation grants, derived work, and child runs;
4. **Memory** — one selected agent's unified, read-only personal event timeline.

Runtime state is not a fifth data silo. It appears in the global header, room participant rows, task rows, and a compact execution drawer because it describes current work owned by those views.

All plugin-owned copy continues through typed Simplified Chinese and English dictionaries.

## Task Center

### Task model shown to the user

The task center groups records by `rootTaskId`. Each root presents:

- title and `open`, `completed`, or `cancelled` state;
- human assignment and current assignee;
- active/expired delegation grants;
- derived tasks with their assigning agent and assignee;
- child runs with parent, terminal status, and a result disclosure;
- related canonical event sequence numbers for traceability.

The UI derives this projection from durable tasks, assignments, grants, child runs, and events. It does not create a second task database.

### Human actions

The user can:

- create and assign a root task to one employed agent;
- explicitly grant that assignee authority to delegate work for the root;
- revoke an active grant;
- cancel an open root or derived task;
- inspect assignments and child results;
- request cancellation of a running child or active top-level task turn.

Creating a root task persists its assignment before waking the assignee. Each delivery mints a branded task-delivery-attempt id; canonical `task/delivery-started`, `task/delivery-accepted`, and `task/delivery-failed` event variants share that id and the task id, while `task/result` identifies the accepted attempt it settles. One task has at most one started or accepted attempt without a terminal failed/result event. A per-task runtime single-flight enforces that rule, and retry is rejected until the prior attempt is terminal. Retry reuses the same open task id and appends a new attempt rather than creating another task. Failures carry only a stable code and display-safe summary. These event-variant fields expand the closed event schema without changing existing aggregate records or the storage-domain version.

Workspace delivery message sources carry workspace id, room/task source id, canonical source-event id, and task-delivery-attempt id when applicable. After materializing a resumed employee session, the Host inspects its durable inbox and session log before allowing new delivery: a still-pending message reconstructs the original queued activity and tracker; a completed correlated turn is terminalized exactly once; an aborted/failed or claimed-without-terminal turn appends the attempt's interrupted failure and becomes retryable. A crash after inbox insertion but before `task/delivery-accepted` is repaired by the persisted message identity instead of creating a second attempt.

### Agent actions

Agent-facing task tools continue to enforce the same policy at the Host boundary:

- work only on a task assigned to the acting agent;
- create a peer subtask only when an active human grant exists for the root;
- run a one-shot child only for an open assigned task;
- complete only an assigned open task.

The Browser cannot forge an agent actor id to bypass those checks.

### Task cancellation

Cancelling a root task atomically marks the root and every open derived task `cancelled`, expires its active delegation grants, and appends canonical cancellation events. Cancelling one derived task affects only that task and its owned child/activity work. After the durable mutation, the Host removes each exact queued delivery message through the owning employee inbox, stops exact active turns, and aborts active children; unrelated inbox work is preserved.

Serialization determines a completion/cancellation race. Completion that commits first makes later cancellation invalid. Cancellation that commits first keeps the task cancelled: a full result that raced with the stop is recorded once as `task/result-after-cancel` for evidence, but it cannot reopen or complete the task; interrupted partial output is not recorded as a task result. Child settlement remains exactly once and never changes the cancelled task state.

## Unified Personal Memory

### Definition

An agent's memory is the ordered set of canonical workspace events referenced by that agent's `memoryEntries`. The same event appears once in that personal timeline even if more than one acquisition path referred to it.

Memory survives room departure, employment departure, re-employment, definition revision changes, profile restart, and browser reconnect. Departed agents remain inspectable but cannot be awakened.

### Memory view

The user selects an agent and sees a read-only newest-first timeline with:

- event sequence and event type;
- source context such as group, direct room, task, or child run;
- actor and subject labels resolved from the same snapshot;
- acquisition provenance: room membership, historical sync, task, or child result;
- textual content and child terminal status when present;
- the definition revision active for model-visible agent output when that fact is recorded.

The view supports stable client-side filters for source, provenance, event type, and sequence range plus case-insensitive text search. One agent/event pair is unique and displays its first acquisition provenance; later attempts to acquire the same event are idempotent. Search is exact over the loaded durable timeline; it is not semantic retrieval and does not change what the model recalls.

There is no edit or delete action in `0.2.0`. Corrections are new events or later lifecycle actions, preserving the append-only evidence model.

## Runtime Status and Control

### Status model

Runtime projection has three explicit layers:

- agent summary: `idle`, `active`, or `failed`;
- activity lifecycle: `queued`, `responding`, `stopping`, or short-lived `settled`;
- activity detail: running tool calls, terminal reason, and display-safe error.

`idle` means the agent has no activity and is therefore not an activity record. `using-tool` is a badge derived from a responding activity's running tool blocks. Runtime-only room failures remain until acknowledged within the current Host process; after restart the summary returns to idle. Durable task delivery failures remain visible in the task center after restart and can make the task-facing summary failed again.

Each activity identifies its agent, a discriminated room or task source, start order, and safe tool/status details. A queued delivery starts with its message id as a stable admission identity; `agent/inbox/claimed` binds it to the exact session id and turn number used by responding, tool, stopping, and settled states. Task deliveries participate in the same projection even though they have no room id.

This projection is ephemeral, but the DSH inbox and Session are durable. A Browser reconnect to the same Host reconstructs it from the activity snapshot and stream. On Host restart the correlation recovery described by the task-delivery protocol reconstructs pending queued activity or deterministically terminalizes the prior attempt before retry is offered; it never assumes that a disappeared projection means the underlying inbox message disappeared.

### Stop semantics

`Stop current turn` targets one exact workspace turn identity. The Host synchronously verifies that the identity still matches the plugin-owned employee handle, session, and active turn, changes its projection to `stopping`, then calls the public `Agent.cancel({ kind: 'user' }, { keepInbox: true })`. Keeping the inbox prevents cancellation from discarding unrelated queued workspace deliveries. The request never targets a generic remote by session id and never aborts an unrelated or later turn that reused the session.

Cancellation is cooperative:

1. the RPC validates that the requested turn is still active and plugin-owned;
2. runtime state changes to `stopping`;
3. the DSH turn settles with an aborted/cancelled reason;
4. the transient projection settles and is retired after durable convergence; an aborted partial assistant reply is not appended to the room and cannot schedule further agent mentions;
5. the original human message and already-recorded tool/session events remain intact.

Stopping a task turn does not automatically mark the durable task cancelled. Task cancellation is a separate human action. The Host keeps an active-child registry keyed by child-run id; stopping a child aborts that exact run and records a terminal `cancelled` result exactly once.

A second stop request while the same turn is already `stopping` returns `already-stopping` and does not call cancel or settle anything again. A stop request after settlement returns `not-active`.

The child controller is registered immediately after the durable child-run id commits and before the first asynchronous start call. One settlement owner arbitrates stop, start failure, result, and disposal races. Startup repairs every durable `running` child without a live registry entry to a terminal `cancelled` result with a stable Host-restart reason before accepting new child work; stopping an already-terminal child returns `not-active`.

The declared DSH `0.1.1-rc.2` compatibility baseline already exposes this cancellation API and persists an aborted turn end. A later DSH compatibility point must prove equivalent semantics in the compatibility matrix before it is declared supported. The Host never simulates cancellation by disposing a whole employee agent or deleting its session.

## Definition Revisions and Selective Synchronization

### Revision history

The colleague view exposes every immutable revision of a definition in number order. Selecting a revision shows its description, instructions, creation event, current/previous distinction, and the agents currently pinned to it. New definition-created/revised events carry the exact revision id. For `0.1.x` history, the Host derives the creation-event association from each definition's ordered revision ids and its corresponding ordered created/revised events.

Saving edits always creates a new immutable revision and makes it the definition's current revision. Existing agents do not change implicitly.

### Save-time synchronization prompt

When the user saves a revision, the UI first asks whether existing agents derived from that definition should be updated. The user can choose:

- update none;
- update all employed and departed instances;
- select individual instances.

The selected ids are submitted in one revise-definition command. The Host creates the immutable revision, validates that every selected agent belongs to the definition, and assigns that same new revision id atomically. Closing the prompt is equivalent to update none.

The UI also permits later synchronization to any existing revision, with an explicit confirmation that names, employment periods, rooms, sessions, and memory are preserved. Synchronization changes role instructions for later turns only; it does not rewrite past events or memories.

## RPC and Host Services

The plugin-owned `/agent-workspace` channel gains explicit endpoints rather than an arbitrary command endpoint:

- task assignment, grant, revoke, cancel, and retry-delivery operations;
- memory projection query by agent and filters;
- runtime active-item snapshot/wait and targeted stop;
- definition revision history and selective synchronization using existing aggregate records.

Every mutation request carries branded ids after parsing, uses the stable Web human identity for human actions, and supplies the Browser's expected aggregate revision. The service compares that revision with the current value inside the serialized `table.update` callback, then returns the committed revision. Stale-revision conflicts return a specific error so the Browser refreshes and asks the user to retry instead of overwriting concurrent changes.

Large memory views use cursor pagination by event sequence. A page cursor is an opaque plugin-owned value and may not encode filesystem or database details.

## Durable Data and Compatibility

The current aggregate already owns definitions, revisions, tasks, assignments, grants, child runs, events, memory entries, and session bindings. `0.2.0` keeps storage-domain version `0`: task cancellation uses the existing `cancelled` status, grant revocation uses the existing `expired` status, and their history plus delivery outcomes are new members of the closed event union rather than new record fields.

New model-visible agent room replies record the definition revision active for that turn. One terminalize-task mutation appends a `task/result` event containing the display-safe textual result and active definition revision and marks the task completed in the same aggregate update. It rejects an already-terminal task, so crash/retry cannot leave a result on an open task or append two terminal results. Historical `0.1.x` replies keep their existing fields and use the best deterministic revision derivation available from agent creation and revision-assignment events; the UI labels an unresolved historical revision instead of inventing one. Ephemeral runtime statuses and UI filters are never added to the durable aggregate.

## Error Handling

- Task actions against departed agents, terminal tasks, missing assignments, or absent grants fail before mutation with localized actionable messages.
- A committed assignment whose wake fails remains open and exposes retry delivery; retry reuses the same task rather than creating a duplicate.
- A stale revision response refreshes the snapshot and preserves unsaved form input.
- Memory pages are snapshot-consistent by aggregate revision; a changed revision restarts pagination rather than mixing states.
- Repeated stop requests after settlement return `not-active` without changing durable state; the Browser treats that result as successful convergence and refreshes activity. The Host does not retain unbounded terminal tombstones merely to repeat a past status.
- Failed tool/turn state is display-safe and does not expose credentials or Host objects.

## Testing Strategy

### Domain and Host

- human root assignment and delivery success/failure/retry;
- grant, revoke/expire, valid peer delegation, and every forbidden delegation path;
- root cancellation cascades through open derived tasks and grants, derived cancellation stays scoped, completion/cancellation races preserve one terminal task state, and task/child activity settles exactly once;
- unified memory survives every lifecycle and revision transition and deduplicates event references;
- memory filter/pagination returns stable results at one aggregate revision;
- queued inbox/session recovery across Host restart, runtime state transitions, exact-identity stop behavior, `already-stopping`, and `not-active` convergence;
- child controller publication/start/result/stop races and startup repair of orphaned `running` records;
- selective revision synchronization for none, all, and a subset;
- stale-revision mutation rejection;
- task results and new room replies retain their active definition revision while legacy derivation remains deterministic.

### Browser

- task tree creation, grant display, delegation/child projections, status filters, and retry/error states;
- unified memory source/provenance filters, search, pagination, and departed-agent inspection;
- idle/active/failed agent summaries; queued/responding/stopping/settled activity; tool/error details; and correctly scoped stop controls;
- revision history navigation and the save-time none/all/subset prompt;
- localized Simplified Chinese and English rendering, including accessibility text;
- reconnect preserves selected view and converges without duplicated task, memory, or runtime rows.

### End-to-end acceptance

A deterministic assembled-profile scenario creates a company role, instantiates multiple colleagues, forms a group with chosen history, assigns a root task, grants one colleague delegation authority, observes peer and child work, inspects each participant's unified memory, changes the role revision for a selected subset, stops one active turn, restarts DSH, and verifies the durable and runtime projections converge.

## Acceptance Criteria

`0.2.0` is complete when a user can perform the full scenario above through the Browser without an internal API, and:

1. every formal task belongs to a root explicitly assigned by a human, and peer-derived work is admitted only through that root's active human grant;
2. no peer delegation succeeds without a human grant;
3. personal memory is unified, durable, attributable, searchable, and read-only;
4. runtime status identifies real owned work and stop never targets another turn;
5. definition updates never silently rewrite existing agents;
6. all new product text is locale-owned;
7. existing `0.1.x` aggregates load with unchanged ids, memory, rooms, and sessions;
8. unit, integration, assembled browser, pack, and registry compatibility gates pass.
