# Agent Workspace v0.1.1 Stability Design

## Status

Approved in chat on 2026-09-02 as the first stage of the three-stage roadmap; the product owner delegated implementation design and code organization.

## Goal

Make `dsh-agent-group@0.1.1` a reproducible maintenance release whose default contributor setup, packed artifacts, public-registry installation, and core browser workflows are all verified against the declared DeepSeek Harness (DSH) compatibility range.

This release does not expand the product model. It removes ambiguity from development and release validation, fixes narrow consistency defects discovered after `0.1.0`, and establishes the verification baseline required by later feature releases.

## Scope

The release contains four workstreams:

1. replace mutable sibling-source links with registry packages in the default development path;
2. add explicit, reproducible DSH source-compatibility checking;
3. verify packed and published packages through clean-profile installation and representative browser workflows;
4. fix direct-room routing, public event typing, reconnect settlement, and client localization defects without changing the durable aggregate format.

## Non-goals

`0.1.1` does not add task, memory, runtime-control, multi-workspace, import/export, or extension UI. It does not add per-agent model, tool, or skill configuration. It does not change the equal-rights agent policy, room memory semantics, employment lifecycle, or human delegation rules.

## Reproducible Dependency Modes

### Default registry mode

The repository's normal `pnpm install --frozen-lockfile`, build, typecheck, and tests must use packages resolved from the public npm registry. Root development dependencies are pinned to one verified DSH release within the packages' declared peer range. The lockfile records those artifacts and must not contain `link:../../deepseek-harness` resolutions.

Published package peer ranges remain the compatibility declaration. Development pins are test inputs, not a narrower consumer requirement.

This makes a fresh checkout independent of the branch, build residue, or removed packages in a neighboring DSH checkout.

A small machine-readable compatibility file is the source for the plugin version, published DSH peer range, registry development pin, and finite named DSH versions/commits verified by source checks. Package manifests, CI, README compatibility text, and release notes validate or render from that file. Later releases extend the same file rather than introducing a second compatibility declaration.

### Explicit source-compatibility mode

Source compatibility is a maintainer operation, not an implicit install behavior. A repository script accepts an explicit DSH checkout path, verifies that the checkout matches a named compatibility point and has the required package manifests, and runs install/build/typecheck/tests in an isolated temporary copy of the plugin with source overrides generated only inside that copy.

The source checkout and plugin working tree are never rewritten. Missing packages, a dirty generated override, or a version outside the requested compatibility point fails before installation with a diagnostic naming the incompatible package or version.

CI uses this mode only for named compatibility points. It must not silently test whatever happens to be at `deepseek-harness/master`.

## Release Verification

### Pre-publish packed-artifact smoke

The existing tarball smoke remains the pre-publish gate. It must:

- build all three packages;
- pack Host, Web, then bundle;
- reject leaked `workspace:` and local `link:` dependencies;
- install the staged bundle into a clean DSH Web profile;
- verify that the profile records and activates `dsh-agent-group`;
- start or load the assembled profile far enough to prove that Host and Web plugins resolve, rather than stopping at static configuration output.

### Post-publish registry smoke

A manual/tag-triggered workflow accepts an exact plugin version and installs `dsh-agent-group@<version>` from the public registry into a new DSH home. It may run only after all three package versions are visible from the registry. The workflow records package manifests, resolved versions, assembled profile output, server startup, and browser-smoke evidence.

The registry smoke never substitutes local tarballs or workspace packages. It is the release evidence for the package users actually receive.

### Browser workflow smoke

A keyless deterministic model/provider fixture first drives the packed-artifact assembled Web profile through these workflows; after publication the same scenario may be rerun with the exact public-registry artifacts:

1. create a definition and a named employed agent;
2. create a group and join the agent with an explicitly chosen memory start;
3. send a group message without a mention and observe no agent wake;
4. send a named mention and observe exactly one durable reply;
5. send `@all` in a group and observe each active member wake once;
6. open/reuse a direct room and send without a mention;
7. observe live turn state, then reload/reconnect and converge on one durable final reply;
8. depart and re-employ an agent and confirm the two-state lifecycle and stable personal memory.

The test uses public package/profile assembly and browser-visible behavior. Domain unit tests remain the lower-level proof for individual invariants.

## Consistency Fixes

### Reserved `@all` in direct rooms

The Host rejects the reserved lowercase `@all` routing token in a direct-room human post even when a caller bypasses the Browser. This validation happens before the room message is appended. Ordinary text containing a different token or casing is not interpreted as the reserved group route.

The Browser continues to hide the `@all` affordance in direct rooms and presents the Host error without clearing the draft.

### Closed workspace event discriminant

`WorkspaceEvent` becomes a closed discriminated union of the event types the aggregate can persist. `child/run-finished` is the sole member requiring `childRunStatus`; every other member forbids it. Aggregate event creation and Zod validation consume the same declared event-type set so TypeScript and durable validation cannot disagree.

This is a public type correction only. Stored event objects and the storage-domain version remain unchanged.

Every durable aggregate record and nested record is validated strictly. DSH validates the schema when loading a storage domain; because its table write methods do not repeat schema parsing, every plugin-owned `table.update` callback explicitly parses the candidate aggregate with `workspaceStateSchema` and runs the relationship invariant before returning it for commit. Unknown fields therefore fail both load and write boundaries instead of being stripped and silently lost on the next aggregate replacement. A copied `0.1.0` record remains valid because strictness changes rejection behavior, not its documented fields.

The aggregate invariant also proves the durable relationships required for later migration and import: every record-map key equals its record id; definition revision lists/current revisions and agent revision references agree; memberships reference their room, agent, and lifecycle events; event ids and sequences are unique; an agent has at most one memory entry for an event; task/grant/child/session references are owned; counters are above every minted id/sequence; and the aggregate workspace id equals its table key.

### Reconnect and settlement convergence

The transient turn stream and durable room log converge by stable workspace-turn identity. Settlement follows one rule: a terminal DSH turn may append at most one durable agent room message, and once that durable revision is visible the equivalent transient projection is retired.

Long-poll cancellation, overlay close, transport reconnect, and repeated snapshot delivery must not surface as agent failures or duplicate terminal rows. A real turn failure remains visible until the durable snapshot and stream snapshot establish its final state.

### Locale-owned client text

All product-visible labels, status text, empty states, errors owned by this plugin, `aria-label` values, and titles move into typed locale dictionaries. The Web package adds `@deepseek-ai/dsh-client-locale` with the same DSH compatibility range to `dsh.client.inject`, peer dependencies, and development dependencies; the Browser Cordis plugin declares the `locale` service in its `inject` list. It augments `LocaleNamespaceMap` with one `agentWorkspace` namespace, registers aligned dictionaries through `ctx.locale.register`, and declares that namespace on both additive slots so their `PropsLocale` receives `t`.

The RPC protocol introduces stable plugin business-error codes for cases such as reserved direct-room routing, departed agents, duplicate membership, stale revision, and invalid task authority. The Browser localizes those codes and their structured safe details. Unknown external failures use one localized fallback plus a display-safe diagnostic; arbitrary English exception text is not treated as localized product copy.

The first release supplies aligned Simplified Chinese and English dictionaries, with the Chinese dictionary defining the key set and the English dictionary statically proving complete alignment. Agent names, room names, definition prose, messages, tool arguments/results, and server-provided user data are never treated as translation keys. The implementation uses only the locale registration and slot translation APIs already public in DSH `0.1.1-rc.2`; it does not import later client-runtime APIs.

## Durable Data Policy

The `agent_workspace` storage domain stays at version `0` for `0.1.1`. No field is added, removed, renamed, or reinterpreted. The release must load a `0.1.0` aggregate without migration and preserve its identifiers, event ordering, memory entries, employment periods, and session bindings.

Any implementation that requires a durable field is out of scope for this maintenance release.

## Error Handling

- An incompatible source checkout fails before package installation.
- Registry publication lag reports which of the three packages is missing and may be retried without mutating a profile.
- Profile startup failure retains logs and the temporary DSH home as CI artifacts.
- Browser workflow failure captures the visible page, console errors, server logs, and the last durable snapshot.
- A rejected direct-room `@all` post leaves the input intact and persists no event.
- Transport cancellation caused by navigation or reconnect is silent; an unexpected disconnect is localized and recoverable through refresh/retry.

## Testing Strategy

### Unit and contract tests

- registry-default lockfile and absence of sibling DSH links;
- source-mode path/version/package validation and isolated override generation;
- direct-room reserved-token rejection before mutation;
- closed event-union compile-time fixtures and Zod parity;
- unknown durable fields are rejected without rewriting the source record;
- successful settlement/reconnect sequences produce exactly one durable reply, agent-turn cancellation produces none, and transport long-poll cancellation does not alter agent settlement;
- every client-owned literal is supplied by typed locale dictionaries;
- a plugin-owned client-copy AST gate rejects hardcoded product text in JSX, accessibility props, and display-format helpers outside the locale module and narrow documented user-data paths;
- packed manifests contain only publishable dependency specifications;
- aggregate relationship, uniqueness, counter, and table-key invariants reject invalid records.

### Integration and browser tests

- clean tarball profile installation and startup;
- clean public-registry profile installation and startup;
- the eight representative browser workflows above;
- uninstall/restart leaves the ordinary DSH Web profile operable and does not mutate core conversation data.

## Acceptance Criteria

`0.1.1` is ready to publish when:

1. a fresh plugin checkout passes frozen install, build, typecheck, and tests without a sibling DSH checkout;
2. explicit source checks pass at every named DSH point in the compatibility file and fail clearly outside it;
3. packed artifacts install and start in a clean profile;
4. the representative browser workflow passes against the packed-artifact assembled profile;
5. direct-room `@all`, event typing, and reconnect duplication defects have regression tests;
6. Simplified Chinese and English UI dictionaries cover all plugin-owned client text;
7. a real `0.1.0` JSON fixture passes boot, mutation, and restart with preserved records and ids;
8. release notes state the exact verified DSH versions and commands used.

Publication is complete only after all three registry packages are visible and the exact-version registry install/start smoke passes. A registry smoke failure stops tag/Release creation and is reported as a release incident; the published version is immutable, so remediation uses a new patch version rather than attempting to overwrite it.
