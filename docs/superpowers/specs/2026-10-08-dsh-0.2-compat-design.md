# Agent Workspace v0.4.0 DSH 0.2 Compatibility Design

## Status

Approved in chat on 2026-10-08. This design defines a compatibility-only `0.4.0` release for DeepSeek Harness `0.2.0-rc.2`. It does not add workspace features or change the durable Agent Workspace record.

## Goal

Make the complete `0.3.0` Agent Workspace product install, load, and operate on DSH `0.2.0-rc.2`. Preserve the definitions, colleagues, employment lifecycle, rooms, unified personal memory, Tasks, delegation grants, child runs, runtime activity, and forward export behavior already shipped in `0.3.0`.

## Version Policy

| Plugin line | Supported DSH range | Verified DSH point |
|---|---|---|
| `0.2.x` | `>=0.1.1-rc.2 <0.1.2-0` | `0.1.1-rc.2` at `b150a551b8d465e31e418e1b2eaf5e79bbb7d28e` |
| `0.3.x` | `>=0.1.7-alpha.2 <0.1.8-0` | `0.1.7-alpha.2` at `00102833dfaee1da9f48a3a8eae9d34005a75218` |
| `0.4.x` | `>=0.2.0-rc.2 <0.2.1-0` | `0.2.0-rc.2` at `639ed015397290b3745d163aafe02ffee4aa3f84` |

One package artifact supports one DSH prerelease line. Existing installations remain on the plugin line matching their Harness version. DSH `0.2.1-alpha.1` is a canary target only and is not included in the published peer range until it independently passes the same source and Browser gates.

## Compatibility Method

The repository's machine-readable compatibility declaration remains the source for the candidate version, DSH peer range, registry development version, and exact verified source commit. Package manifests, lockfile, source compatibility command, CI checkout, README matrix, and release notes must agree with it.

The first compatibility run compiles the unchanged `0.3.0` source against the exact DSH `0.2.0-rc.2` checkout. Each compiler or runtime failure is handled at the public API consumer that owns it. Type-only changes use compile failures as the initial evidence. Behavioral changes require a focused failing regression before production code changes.

The adaptation may update public API imports, lifecycle calls, client module requests, profile patch metadata, and test fixtures. It may not broaden the peer range based only on successful compilation or an exact-version exemption.

## Durable Data and Runtime Semantics

Storage-domain version `0`, workspace aggregate fields, identifiers, event ordering, employment periods, room history, task history, agent session bindings, memory provenance, and forward export format version `1` remain unchanged. No migration or rewrite is introduced.

Employee sessions remain hidden from ordinary DSH conversation grouping while idle. Delivery temporarily restores the bound session, waits for the employee Agent to become idle, and archives it again. Failed creation, resume, delivery, retirement, plugin disposal, and route disposal must release every acquired handle and registration.

The behavior policy remains fixed:

- a mentioned colleague must reply;
- an unmentioned colleague does not speak;
- colleagues may mention one another;
- a colleague may create a one-shot child when appropriate and may ask the human first;
- only a human-explicitly delegated colleague may allocate formal peer work;
- ordinary colleagues work only after explicit human assignment;
- each colleague has one unified personal memory across joined rooms and direct communication.

## Browser Integration

The Web package remains additive. It registers the Workspace launcher and overlay without replacing core DSH conversation surfaces. It uses only public DSH client modules and the plugin-owned authenticated `/agent-workspace` route.

The emitted Browser bundle must resolve every external request from the DSH `0.2.0-rc.2` module table. The Host route registration remains effect-owned so uninstall and hot reload remove it. Client store, localization, layout, renderer, sidebar, and UI primitive changes are adapted without duplicating DSH's conversation renderer.

## DSH 0.2.1 Canary

After `0.2.0-rc.2` is green, run a read-only source compatibility probe against DSH `0.2.1-alpha.1` commit `5badb15009ae1756c3afe0ae0cef1faafc290ccc`. Record compiler and manifest differences, including the upstream removal of runtime invariant package exports.

The plugin's `assertWorkspaceInvariants` is product-owned aggregate validation, not a DSH runtime invariant plugin. It remains in place. The canary result may inform the next release but does not change `0.4.0` dependencies, peer ranges, documentation claims, or release gates.

## Verification

The release gate must prove:

1. package versions, peer ranges, registry development dependencies, CI source checkout, documentation, and compatibility metadata agree;
2. unchanged `0.3.0` durable fixtures load without rewriting workspace data or employee session identities;
3. build, typecheck, and all unit tests pass against exact registry packages for DSH `0.2.0-rc.2`;
4. an isolated source copy builds, typechecks, and passes all tests against exact commit `639ed015397290b3745d163aafe02ffee4aa3f84`;
5. the Browser bundle contains no private DSH source import and resolves its external modules from the verified DSH Web composition;
6. all three packed `0.4.0` artifacts install into a clean DSH Web profile without a compatibility exemption;
7. two consecutive real Browser workflows pass without retry, covering definitions, colleagues, group membership, direct rooms, mentions, task assignment and delegation denial, unified memory, runtime streaming and stop, re-employment, definition revisions, Host restart persistence, uninstall, and preservation of a core DSH session;
8. Browser console and network error evidence is empty, successful scratch profiles are removed, and no smoke server remains;
9. a final whole-branch review has no unresolved critical or important finding.

Tests use the deterministic local scripted provider. They verify DSH integration and durable behavior without making a live model API request.

## Release Boundary

The implementation produces a local, reviewed `0.4.0` candidate. Publishing npm packages, creating or moving a tag, creating a GitHub Release, merging into the default branch, and pushing are separate release actions.

## Non-goals

- Supporting DSH `0.1.7` and `0.2.0` in one artifact.
- Claiming support for DSH `0.2.1-alpha.1`.
- Changing Agent Workspace storage or forward export formats.
- Adding import, multi-workspace management, model/tool/skill selection, or new agent rights.
- Adopting removed DSH runtime invariant exports; the plugin's own domain validation is unrelated.

## Acceptance Criteria

`0.4.0` compatibility work is complete when every verification item passes against exact DSH `0.2.0-rc.2`, the compatibility matrix directs each DSH line to the correct plugin line, the final diff preserves `0.3.0` product and data semantics, and the unpublished candidate is ready for a separate release decision.
